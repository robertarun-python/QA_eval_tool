Score these five areas, each 0-20 (total 100), using PRIMARY EVIDENCE only:

1. automation_design (0-20) - does the code faithfully automate the candidate's OWN design? Right flow, reuses the provided helpers rather than reinventing them, structured so it could be run repeatedly.
2. test_data_and_assertions (0-20) - do the encoded data and assertions actually come from the candidate's design, and do the assertions PROVE the stated requirement? Judge whether an assertion would genuinely fail if the requirement were broken. DO NOT score on the NUMBER of assertions - one assertion that proves the requirement beats five that restate it or check something incidental. A test that passes for the wrong reason (asserting on a value the code itself just set, never checking the real outcome, or asserting nothing meaningful) is a serious weakness here regardless of count.
3. ai_usage (0-20) - were the prompts specific, grounded in their own design, and appropriately scoped? Asking the assistant to encode a stated step is good use. Trying to get it to invent cases, data or assertions is poor use - note it, and note that the assistant refusing is not itself a candidate failure. A necessary clarification question from the assistant is valid AI usage and must not itself be penalized; the candidate's own resolution of that clarification is evidence of specification quality, and should be judged as such. The AI must not receive credit here for inventing an important automation decision (a case, a data value, an assertion, a design choice) that the candidate never specified or reviewed - that is a weakness in this area, not a strength.
4. ai_output_review (0-20) - is there evidence the candidate actually reviewed what the assistant produced rather than accepting it wholesale? Where a turn carries planted_flaw, whether the final code still contains it is the strongest single piece of evidence here. Look for their own edits, corrections, follow-ups that catch a problem, or a rejected suggestion. Accepting a correct suggestion unchanged is acceptable; never examining anything is not.
5. execution_and_validation (0-20) - did they run it, and does the run's own result (checked against the ground truth above) actually prove the expected result, or only exit cleanly without proving it? Since there is no candidate-written interpretation to read, judge this from final_code and execution_result together: a test that exits 0 by checking something that can't actually fail (a value the code itself just set, an incidental condition) scores poorly here even though it "passed" - execution PASS alone is not proof of correct automation, and running the code is not by itself evidence of strong automation engineering. A candidate whose FINAL code (after any review/fix) genuinely checks the real outcome scores well, whether or not that took more than one turn to get there.

final_score is the sum of the five (0-100).
